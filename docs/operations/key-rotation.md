# Producer key handling and rotation

The producer key is the validator's identity: whoever holds it can produce
blocks. A copy of the key is a copy of the right to produce. Treat the key file
as a secret, keep it `0600`, and store backups with restricted access.

## Current format

Node start-up on `main` still reads the plaintext 32-byte BLS scalar in
`<data-dir>/producer.key` (hex, `0600`), generated by `subhost init` when
missing. The encrypted producer keystore crate and CLI (S9.6, `subhost producer
create/inspect/unlock/migrate`) **are merged** (PR #59); see
[producer-keystore.md](producer-keystore.md). What is still pending is encrypted
**node start-up** (Track A's `bootstrap_with_producer_key`, Q-018, sequenced
after S6.2): until it lands, a running node uses the plaintext file, and the
keystore is managed through the CLI. `subhost producer migrate` does **not**
encrypt in place — it writes a **separate** `producer.keystore.json` and
preserves the plaintext source on success and on every failure; removing the
source is an explicit later operator action. When encrypted node start-up
lands, the node will unlock the keystore with an owner-only credential file —
no implicit plaintext fallback.

## Protecting the identity

- Keep `producer.key` (and any backup) `0600`, owned by the service user.
- Back it up separately from the ledger if it lives outside the data directory.
  A ledger backup that includes the key file also includes the identity; restrict
  access accordingly (see [backup-restore.md](backup-restore.md)).
- Never run a second producer with the same identity alongside the original
  node: two signers with one key can equivocate and halt the chain on
  conflicting final evidence.

## What rotation means here

There is **no online validator-set change protocol** on `main`. A producer key
is bound into `genesis.json` as a validator public key with a proof of
possession. You cannot rotate a live validator's key by swapping the key file:
the new key would not match the genesis validator, and blocks signed with it
would not authenticate against the committed validator set.

Rotation therefore happens at genesis, not in place:

1. Generate a new identity into a **fresh** data directory:
   `subhost init --data-dir <new-dir> --validator <ADDRESS>:<POWER>` (the new
   producer key is generated and its public key/PoP written into the new
   genesis). Use a new chain ID for a new chain.
2. Coordinate the cut-over with every validator: a re-genesis changes the
   consensus context, so all participants must adopt the new genesis together.
   Preserve the old data directory and keys; do not delete them.
3. Start the new chain from the new genesis. The old chain's finalized history
   stays append-only and is never rewritten.

If you only need to move the same identity to new hardware (not change the key),
copy the existing `producer.key` and genesis to the new host with permissions
intact, and stop the old node first so only one producer signs. This is a
migration, not a rotation; the identity is unchanged.

## Encrypted keystore (S9.6, merged)

The crate and CLI are on main (PR #59); encrypted **node start-up** is the
pending Track A piece. Until it lands, manage the keystore through the CLI and
keep the plaintext `producer.key` for the running node.

- Encrypt an existing plaintext key: `subhost producer migrate` writes a
  **separate** `producer.keystore.json` (it does not modify the source),
  preserves the source on success and failure, checks genesis membership, never
  replaces an existing keystore, and verifies by authenticated read-back.
  Removing the plaintext source afterwards is an explicit operator action;
  deletion cannot promise physical erasure on SSD/COW/backup systems.
- Create a new encrypted identity: `subhost producer create`.
- Unlock/verify: `subhost producer unlock` / `inspect`. Passwords come from
  non-echo prompts or an owner-only credential file; there is no password
  argument. Losing the password loses the identity — there is no recovery.
- Rotation semantics are unchanged: the keystore wraps the same genesis-bound
  identity; changing the validator key still requires a coordinated re-genesis.

## What not to do

- Do not swap `producer.key` on a live validator and expect it to keep producing.
- Do not delete `fork-incidents.bin` or the journal to "reset" an identity.
- Do not reuse one producer key across two running nodes.
- Do not assume deleting the plaintext file after migration erases it physically
  (SSD/COW/backup systems retain copies); the migrate command says so plainly.
