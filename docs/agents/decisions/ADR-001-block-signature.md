# ADR-001: BLS12-381 block signatures with a dedicated producer key

- Status: accepted
- Date: 2026-11-18
- Settles: `Q-001`
- Tracks: A (implementation), B (key file and `subhost init`)

## Context

S1 makes block production authenticated: a produced block carries one
`ValidatorSignature` over `Block::signing_payload()`, and `accept_block` verifies it
against the genesis validator set. S0.2 already pinned the payload bytes, so the
remaining decision was which scheme signs them and which key holds the secret.

S2 needs BLS votes and quorum certificates regardless. `subhost-consensus` already
stores BLS public keys and gates registration on a proof of possession.
`subhost-wallet` stores ed25519 keys behind a password-prompted keystore.

## Decision

Use **BLS12-381** for block signatures, one key per validator, read from a producer
key file that is separate from the ed25519 wallet keystore.

- The signed bytes are the S0.2 layout:
  `BLOCK_SIGNING_DOMAIN || chain_id_be_u64 || height_be_u64 || block_hash`.
- The signature is stored in `Block.signatures` as
  `ValidatorSignature { validator, signature }`; the list itself is not signed.
- Signatures are 96 bytes and public keys 48 bytes, matching
  `subhost-consensus`.
- A node started with `--validator` must have a producer key file, and refuses to
  start without one. The file is mode 0600 and is not the wallet keystore.

Track B's two conditions are accepted and are part of the contract:

1. **The proof of possession is mandatory and is generated by `subhost init`.**
   Genesis stores the proof, and registration verifies it. A `from_genesis` that
   skips validators with an empty proof is not acceptable, because that turns the
   rogue-key defence off silently.
2. **The proof of possession has its own domain tag**, separate from the shared
   `BLS_DOMAIN` that block and vote signatures use.

## Consequences

- S1.1 (registry from genesis) and S1.4 (node/CLI wiring) complete the feature
  together: S1.1 adds the constructor that validates proofs, and S1.4 makes
  bootstrap its first caller. S1.1 on its own is inert, because nothing calls
  `from_genesis` yet, so what a node accepts does not change until S1.4 lands.
- `ValidatorInfo.proof_of_possession` stops being optional in practice. The field
  stays `#[serde(default)]` so pre-S1 genesis files still deserialize, but a genesis
  file without proofs now fails registration instead of loading quietly.
- A test asserts that the block payload and the QC payload
  (`subhost-qc-v1 || view || block_hash`) never collide for the same height and
  hash. They differ in prefix and length today; the test makes that a contract.
- `SECURITY.md` must not claim BLS interoperability. `subhost-crypto` uses
  hash-and-multiply over SHA3-384, not RFC 9380 `hash_to_curve`, and its module docs
  already say so. Moving to a standard ciphersuite is an S2 or S12 item.
- `subhost-cli` is Track B's file, so the `init --validator` work is a Track B
  change against this ADR. `subhost-crypto` is not named in either track's file
  list; the one-line PoP domain addition is taken by Track A under S1.1, and Track B
  can veto it in review if it prefers to own that file.

## Alternatives rejected

- **ed25519 for blocks.** Reuses the wallet keystore and the transaction signature
  code, but cannot aggregate, and S2 still needs BLS. Validators would end up with
  two keys, two rotation paths, and a mapping between them.
- **ed25519 blocks plus BLS votes.** Each piece uses its natural scheme, at the cost
  of the same two-key lifecycle plus more CLI surface.
