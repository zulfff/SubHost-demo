## Answer

Agree: **BLS12-381**, one producer key per validator, in a producer key file that is
separate from the ed25519 wallet keystore. The S0.2 payload layout
(`BLOCK_SIGNING_DOMAIN || chain_id_be_u64 || height_be_u64 || block_hash`) is
unambiguous and commits to every header field, so Track B accepts it as written.

Two conditions before S1.1 calls `ValidatorRegistry::register` from genesis:

1. **The proof of possession must be mandatory, and generated by `subhost init`.**
2. **The proof of possession needs its own domain tag**, not the shared `BLS_DOMAIN`
   that block and vote signatures use.

Neither condition changes the block format. Both are cheap now and expensive after a
genesis file is published.

## Reasoning

**Why BLS and not ed25519.** S2 needs BLS votes and quorum certificates, and the
consensus crate already implements them. Choosing ed25519 for blocks means every
validator holds two signing keys, two rotation paths, and a mapping between them;
the only thing it buys is a 64-byte signature instead of 96 at one block per second.
That is not a trade worth two key lifecycles.

**Why a separate producer key file.** The wallet keystore is an ed25519 key behind a
user password prompt. A validator has to sign unattended at boot and on every view.
Reusing the keystore would either run a node with a password in the environment or
weaken the keystore. A dedicated `--producer-key-file` (mode 0600, refuse to start
`--validator` without it) keeps the two key lifecycles honest.

**Why the payload layout is fine.** `block_hash` already covers `state_root`,
`tx_root`, `receipt_root`, `parent_hash`, `gas_used`, `gas_limit`, and `timestamp`,
and the signature list is correctly excluded so signing is not circular. The domain
tag makes a block signature unusable as a vote signature: the QC payload is
`subhost-qc-v1 || view || block_hash` (`subhost-consensus/src/lib.rs:326`), a
different prefix and a different length. Keep both tags distinct and add a test that
asserts the two payloads never collide for the same height and hash.

**Why the PoP conditions matter.** `ValidatorRegistry::register` rejects a validator
whose proof does not verify (`subhost-consensus/src/lib.rs:74`), and aggregate
verification over a shared message is only safe with verified proofs
(`subhost-crypto/src/lib.rs:109`). Today `subhost-cli` builds every genesis validator
with an empty proof (`subhost-cli/src/main.rs:389`), so a `from_genesis` that
registers them will reject the whole set. S1.1 and S1.4 have to land together: `init
--validator` generates the proof, genesis stores it, registration verifies it.

On the domain tag: `BLSScheme::proof_of_possession` signs the raw 48-byte public key
encoding with the shared `BLS_DOMAIN` (`subhost-crypto/src/lib.rs:122,147`). There is
no collision *today* because block payloads are 64 bytes and QC payloads 56, but the
BLS signature draft uses a dedicated PoP domain
(`BLS_POP_BLS12381G2_XMD:SHA-256_SSWU_RO_POP_`) and a dedicated signing domain
(`BLS_SIG_..._POP_`). Matching that now costs one prefix constant; changing it after
genesis files exist costs a migration.

**One limitation to write down, not fix in S1.** `subhost-crypto` uses
hash-and-multiply over `Sha3_384`, not RFC 9380 `hash_to_curve`, and it says so in
its module docs (`subhost-crypto/src/lib.rs:5-9`). That is acceptable for our own
signatures and unacceptable for interoperating with another BLS implementation, so
`SECURITY.md` must not claim BLS interoperability. Moving to a standard ciphersuite
is an S2 or S12 item, not something to smuggle into S1.

## Evidence

- `crates/subhost-core/src/lib.rs:299` — `Block::signing_payload` and its layout.
- `crates/subhost-core/src/lib.rs:510` — `ValidatorInfo.proof_of_possession`, empty by default.
- `crates/subhost-crypto/src/lib.rs:27,122,147` — one shared `BLS_DOMAIN`; PoP signs the raw key encoding.
- `crates/subhost-crypto/src/lib.rs:6-10` — the non-standard hash-to-curve limitation is already documented.
- `crates/subhost-consensus/src/lib.rs:22,24,74,326` — 96-byte signatures, 48-byte keys, PoP-gated registration, distinct QC domain.
- `crates/subhost-cli/src/main.rs:389` — genesis validators are created with an empty proof.
- https://www.ietf.org/archive/id/draft-irtf-cfrg-bls-signature-06.txt — ciphersuite
  `BLS_SIG_BLS12381G2_XMD:SHA-256_SSWU_RO_POP_` and a separate PoP domain
  `BLS_POP_BLS12381G2_XMD:SHA-256_SSWU_RO_POP_` (verified 2026-11-18).
- https://www.rfc-editor.org/rfc/rfc9380.txt §J.10.1 — `BLS12381G2_XMD:SHA-256_SSWU_RO_`
  is the standard hash-to-curve suite the current implementation does not use
  (verified 2026-11-18).

## If disagree

Nothing here asks Track A to reopen the scheme decision. If Track A prefers to keep
the PoP on the shared domain for S1 and file the ciphersuite change as a follow-up, I
will not block on it **provided** `SECURITY.md` records both: the PoP has no
dedicated tag, and the hash-to-curve is not RFC 9380. What I will object to is
shipping `from_genesis` that silently skips registration when the proof is empty —
that turns the rogue-key defence off without saying so.
