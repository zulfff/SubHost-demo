Subhost Web3 / engineering reference

Build against what exists.

Subhost is a Rust workspace for a decentralized cloud protocol. These docs describe the code that runs today, the interfaces you can call, and the pieces that are still deliberately unfinished.

!
Pre-production software. Consensus block production, EVM/WASM/zk execution, persistence, and live cross-chain settlement are not wired into the node yet.
ImplementedCore types

Addresses, hashes, transactions, blocks, receipts, and genesis config.

ImplementedState + mempool

In-memory balances, nonces, fee accounting, bounded transaction admission.

PartialRPC + networking

Useful local surfaces with explicit limits; no production node loop yet.

Not wiredExecution layer

EVM, WASM, and zk crates are placeholders in this repository.

Start here

Quickstart

Get a local Subhost binary and inspect the surfaces that are implemented today. This is a development workflow, not a testnet deployment guide.

Prerequisites

  • Rust 1.75 or newer
  • Approximately 4 GB RAM for the full workspace; use two Cargo jobs
  • A Unix-like shell for the commands below

Build and initialize

shell
cargo check --workspace -j 2
cargo run -p subhost-cli -- init --chain-id 1 --data-dir ./data

The genesis command creates the directory and writes a genesis configuration. A zero-validator genesis is rejected by validation and is not a production network configuration.

Start the local RPC surface

shell
cargo run -p subhost-cli -- node --listen 127.0.0.1:8545

The current node exposes a local JSON-RPC subset. It does not run a complete consensus/block-production loop, so transaction receipts remain null until a confirmation backend exists.

Smoke test

shell
curl -s http://127.0.0.1:8545 \\
  -H 'content-type: application/json' \\
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_chainId","params":[]}'
{"jsonrpc":"2.0","result":"0x1","id":1}

Boundaries that matter

A

Identity

RPC binds the submitted from address to a supplied Ed25519 public key. The signature covers the canonical unsigned transaction.

B

Replay

State requires the exact account nonce and increments it with checked arithmetic. IBC tracks received packets and acknowledgements.

C

Resource limits

RPC request bodies, batches, responses, connections, mempool payloads, and network transmit size are bounded.

D

Truthful status

Receipt queries return null until a producer/confirmation path exists. Placeholder engines are labeled rather than silently invoked.

Integration reference

JSON-RPC

The RPC server is a deliberately small Ethereum-shaped surface for local development. All quantities are strict 0x-prefixed hex strings.

eth_chainIdread

Returns the configured numeric chain ID as a quantity. Default CLI state is chain 1.

→ "0x1"
eth_blockNumberread

Returns the atomic block-height counter. It starts at 0x0 until a producer advances it.

→ "0x0"
eth_getBalanceread

Parameters: [address] or [address, block]. Reads the in-memory state balance.

→ "0x0"
eth_gasPriceread

Returns the current local default gas price, 0x1.

net_versionread

Returns the chain ID as a decimal string for Ethereum tooling compatibility.

eth_getTransactionReceiptpending

Returns null. There is no connected block producer or confirmation store yet.

Signed transaction submission

eth_sendTransaction accepts one object. Required identity fields are from, publicKey, and signature. The public key is 32 bytes, the signature is 64 bytes, and both must be 0x-prefixed. The derived address must equal from.

noncequantityMust equal the current account nonce.
chainIdquantityMust equal the server chain ID.
valueu128 quantityDefaults to zero.
gasPriceu128 quantityDefaults to 0x1.
gasLimitquantityDefaults to 0x5208.
databytesHex-encoded calldata; mempool bound is 128 KiB.
i
The signature is verified over a bincode-encoded transaction with a zeroed signature field. This is an internal protocol surface, not a claim of full Ethereum transaction wire compatibility.
Developer tooling

CLI reference

The binary is named subhost. Commands below reflect the Clap surface in crates/subhost-cli; some commands report prerequisites instead of pretending a backend exists.

Node lifecycle

subhost init --chain-id 1 --data-dir ./dataWrite genesis configuration.
subhost node --listen 127.0.0.1:8545Start the local node/RPC surface.

Wallet

subhost wallet new --password <pass>Create an encrypted wallet.
subhost wallet listList local wallet files.
subhost wallet export <address> --password <pass>Decrypt and export a private key.

Transactions

subhost tx send --from <addr> --to <addr> --amount 1000Build a local transaction and print its hash.
subhost tx status <hash>Inspect status; confirmation needs a live backend.

Queries

subhost query balance <address>Query a running node.
subhost query block --height 123Block lookup interface; producer backend is not wired.
subhost query validatorsValidator query surface.

Contract surface

subhost contract deploy --code <path>CLI surface exists; execution backend is not implemented.
subhost contract call --address <addr>CLI surface exists; EVM/WASM engines remain placeholders.

Security notes

Security model

The repository treats input validation and truthful failure as protocol behavior. The threat model is broader than the current implementation, so each roadmap mitigation is labeled accordingly.

Input boundaries

RPC quantities, addresses, signatures, data payloads, request bodies, batches, and network messages are bounded or rejected.

Cryptographic hygiene

Private material is zeroized where practical; X25519 rejects all-zero shared secrets; BLS identity points are rejected.

Accounting integrity

Transfers debit the sender, charge fees, reject insufficient balances, bind transactions to a chain ID, and enforce exact nonces.

Fail closed

Consensus QC validation does not accept arbitrary signature bytes while the validator public-key registry is absent.

!
Not implemented: encrypted mempool, Dandelion++ privacy, threshold encryption, production consensus loop, HSM program, oracle/MEV defenses, and a live bug bounty program.

Reporting

Do not publish suspected vulnerabilities in an issue first. Follow SECURITY.md and include the exact commit, file/line, impact, reproduction, and mitigation.
